# ۲۴ سپتامبر ۲۰۲۶

## git — رفع خطای «unable to locate a suitable SDK»

**علامت:** هنگام push/pull در پنل Source Control پیام
`Git: git: error: unable to locate a suitable SDK for the system` دیده می‌شد.

**ریشهٔ تأییدشده:** نصب CommandLineTools ناقص است. در
`/Library/Developer/CommandLineTools/SDKs/` فقط سیم‌لینک‌ها مانده‌اند
(`MacOSX.sdk -> MacOSX15.2.sdk`, `MacOSX15.sdk -> MacOSX15.2.sdk`, ...) و مقصدها وجود ندارند.
`xcrun --sdk macosx --show-sdk-path` خطا می‌دهد. `xcrun`/`strings`/`otool` هم همان پیام را چاپ می‌کنند.
سیستم: macOS 26.0 (25A354)، Xcode نصب نیست.

**نکتهٔ مهم:** خودِ `/usr/bin/git` (Apple Git 2.39.5) با وجود این پیام **کار می‌کند** و `fetch` با exit 0
برمی‌گردد؛ پیام روی stderr است. مشکل واقعی این است که پنل Source Control آن را به‌عنوان خطا نشان می‌دهد.

**یافتهٔ دوم:** helper کیچین نسخهٔ Homebrew خراب است.
`/opt/homebrew/opt/git/libexec/git-core/git-credential-osxkeychain` هم برای `get` و هم `store`
با `failed to get: 100001` رد می‌شود (ناپایدار؛ گاهی روی ورودی ساده هم می‌شکند) و در نتیجه
`git fetch` می‌گوید `could not read Username`. در مقابل، helper خودِ git اپل در
`/Library/Developer/CommandLineTools/usr/libexec/git-core/git-credential-osxkeychain` سالم است
و توکن را از کیچین می‌خواند.

**اصلاح انجام‌شده (بدون sudo):**
- `~/.local/bin/git` → سیم‌لینک به `/opt/homebrew/bin/git` (نسخهٔ 2.55.0). چون `~/.local/bin/env`
  در `.zshrc` این مسیر را اول PATH می‌گذارد، `git` حالا Homebrew است و هیچ پیام SDK نمی‌دهد.
- در `~/.gitconfig` بخش `[credential]` اضافه شد: اول `helper =` خالی (لیست helperهای سیستم را
  ریست می‌کند تا helper خراب Homebrew رد شود)، سپس
  `helper = /Library/Developer/CommandLineTools/usr/libexec/git-core/git-credential-osxkeychain`.
- تأیید در شل تمیز (`env -i ... zsh -l -i`): `which git` → Homebrew، `git fetch origin` با exit 0 و
  بدون هیچ خروجی، و `git push --dry-run` فقط «non-fast-forward» داد ⇒ احراز هویت push هم سالم است.

**اصلاح ریشه‌ای (باقی‌مانده، نیاز به sudo کاربر):**
`sudo rm -rf /Library/Developer/CommandLineTools && sudo xcode-select --install`
تا `xcrun`/`strings`/`otool`/کامپایلر هم سالم شوند. بعد از آن می‌توان سیم‌لینک و override را ساده کرد.

**وضعیت مخزن:** `main` نسبت به `origin/main` یک commit جلو و سه commit عقب است؛ قبل از push باید
pull شود (انتخاب merge یا rebase با کاربر است).

**تلهٔ سندباکس:** نوشتن در `~/.gitconfig` و `security add-internet-password` در سندباکس Bash با
«Operation not permitted» رد می‌شوند. برای ویرایش فایل‌های خانه از ابزار Edit استفاده کن، نه
`git config --global` یا `security`.

## git — دور دوم: خطای واقعی «divergent branches» و merge واگرایی

**تصحیح تشخیص قبلی:** خطای SDK واقعاً رفع شده بود. لاگ `vscode.git` نشان داد اپ همان git درست را
برداشته است: `Using git "2.55.0" from "/Users/heidarian2/.local/bin/git"`. پس سیم‌لینک `~/.local/bin`
برای اپ هم کار می‌کند (اپ PATH را از شل login+interactive می‌گیرد).

**خطای واقعی:** در `git pull --tags origin main` (همان دستوری که دکمهٔ Sync اجرا می‌کند):
`fatal: Need to specify how to reconcile divergent branches.` چون `main` واگرا بود
(۲ commit جلو / ۳ عقب) و `pull.rebase`/`pull.ff` تنظیم نبود.

**اصلاح:** `git config pull.rebase false` (محلی، در `.git/config`) ⇒ استراتژی merge.
بعد `git merge origin/main` و حل ۴ تعارض:

- `database/content/activity.json` — هر دو طرف دقیقاً ۵۰۰ ورودی (سقف `ACTIVITY_LIMIT = 500` در
  `contentStore.js`، جدیدترین اول). اجتماع بدون تکرار بر اساس `id`، مرتب بر `createdAt` نزولی،
  برش به ۵۰۰ ⇒ ۷۷۲ → ۵۰۰.
- `database/content/events.json` — اجتماع بر اساس `id` (۳۳۶ + ۱۶، بدون هم‌پوشانی) ⇒ ۳۵۲.
  سقف `EVENTS_LIMIT = 20_000` + فیلتر ۱۸۰ روز در `analyticsStore.js`.
- `database/content/admins.json` — فقط دو زمان `updatedAt`/`lastLoginAt` فرق داشت؛ نسخهٔ
  `origin/main` (۲۰۲۶-۰۹-۲۳) جدیدتر بود ⇒ همان.
- `.workbuddy-ai/memory/MEMORY.md` — هر دو نسخه محتوای یکتای ارزشمند داشتند (ریموت: معماری پنل/
  میکرودرسنامه/فلش‌کارت و تله‌های هارنس؛ محلی: دیزاین‌سیستم/بررسی‌های مجاز/محیط). اجتماع کامل،
  بدون حذف چیزی، در ساختار بخش‌بندی‌شده.

**تأیید:** `git pull --tags origin main` در شل تمیز ⇒ exit 0 و «Already up to date».
merge commit = `752f2d1`؛ وضعیت پس از merge: `main...origin/main [ahead 3]` (فقط جلو، دیگر عقب نیست).

**درس:** برای دیدن خطای واقعی پنل VS Code، لاگ
`~/Library/Application Support/Code/logs/<ts>/window1/exthost/vscode.git/Git.log` را بخوان —
نوتیفیکیشن «Git: From https://github.com/...» فقط خط اول خروجی pull شکست‌خورده است، نه خطای اصلی.

## فلش‌کارت پنل — تکمیل «کتابخانهٔ کاربران» (دور پنجم، ظهر)

**خواستهٔ کاربر (سه بند، بعد از یک ابهام‌گیری شفاف):** (۱) همهٔ مجموعه‌های کتابخانهٔ تپشِ
کاربران در بخش فلش‌کارت پنل دیده شوند، (۲) ساخت و افزودن کارت مثل رابط گرافیکی کاربران باشد،
(۳) **باگ:** ساخت مجموعه و کم/زیاد کردن کارت در پنل باید در بخش کاربران دیده شود
(«کار پنل و کتابخانهٔ کاربران یک چیز واحد»). برای دک‌های ثابت هم «رکورد قابل ویرایش در پنل»
انتخاب شد. بدون تست رابط کاربری.

**نکتهٔ روش:** بند سوم دو خوانش متضاد داشت («نگهبان» = نباید برسد / «باگ» = باید برسد).
به‌جای حدس، یک `AskUserQuestion` دوگزینه‌ای پرسیده شد؛ یک رفت‌وبرگشت ولی جلوی پیاده‌سازی
معکوس را گرفت. این الگو برای این کاربر جواب می‌دهد.

**سرور (`contentStore.js`):** `syncFlashcardDecks()` در `ensureStore()` هر دک ثابتِ بدون رکورد
را از `TAPESH_DECKS`/`TAPESH_CARDS` به رکورد کامل تبدیل می‌کند (`status: 'published'` چون
همین حالا زنده است، `origin: 'tapesh'`)، کارت‌ها **همان `id`** را نگه می‌دارند (وگرنه وضعیت
مرور کاربران صفر می‌شد) و `source`/`language` هم حمل می‌شوند (`carriedCardFields`) تا نخستین
ویرایش، منبع کارت را پاک نکند. دو محافظ مثل `syncMicroCourses`: `flashcardSynced` یک‌بار در
عمر پروسه و `writeJson` مستقیم. backfill تک‌فیلدی `origin: 'panel'` برای رکوردهای قدیمی.
`origin` از بدنهٔ درخواست خوانده نمی‌شود، فقط از رکورد قبلی ارث می‌رسد.

**کلاینت (`flashcardService.js`):** `publishedDeckIds()` و حذف هم‌شناسه‌ها از `TAPESH_DECKS`/
`TAPESH_CARDS` — بدون آن هر دک ثابت دو بار می‌آمد (`cardCount` دو برابر) و ویرایش پنل زیر
نسخهٔ کد گم می‌شد.

**پنل (`AdminFlashcards.jsx`):** پیش‌فرض `EMPTY_DECK.status` از `draft` به `published` رفت
(بند سوم)؛ `CardEditor` به `CardForm` + `CardEditorModal` تبدیل شد و فهرست کارت‌ها ردیفی شد
(`.ad-fccard__rows`) — همان جریان «ساخت کارت» کاربران. `ad-fccard__head` بی‌مصرف شد و رفت.
نشان «تپش» با `origin` در `.ad-deckcell`.

**تأیید:** سرور **۲۰/۲۰** (بدون باندل)، کلاینت **۱۰/۱۰** آنلاین + **۴/۴** آفلاین (باندل‌شده)،
رندر jsdom **۱۵/۱۵**، و `adminApi.test.mjs` **۹۲/۹۲**. سه تلهٔ هارنس: (۱) کارت جعلی بدون
`status: 'active'` در `fetchDeck` فیلتر می‌شود؛ (۲) `fetchDeck` فقط دک‌های `libraryAdded` را
می‌دهد پس اول `addLibraryDeck`؛ (۳) در پاک‌سازی، شکل **رکورد** را به `updateFlashcardDeck`
برگردان نه خروجی عمومی — خروجی عمومی `status` ندارد و دک بی‌صدا `draft` می‌شد (۱۱ دک/۵۴ کارت

**⚠️ نویسندهٔ موازی واقعاً فعال بود:** وسط کار، session دیگری `database/contentStore.js` را

## دور ششم — تصویر کارت: فرمت‌های رایج + سقف ۴ مگابایت (پنل و داشبورد)

**درخواست:** «فقط در بخش کارت‌های تصویری، از فرمت‌های مختلف تصویر پشتیبانی شود، حجم عکس‌ها هم
بیشتر از ۴ مگ نباشد.» دو خوانش داشت (پنل در برابر داشبورد) و چون **هر دو جا چیپ «تصویری»** دارند،
`AskUserQuestion` پرسیده شد؛ پاسخ: **هر دو** + «فرمت‌های رایج مثل png/jpg/heic و باقی فرمت‌های معروف».

**تک منبع حقیقت:** `CARD_IMAGE_MIME_EXTENSIONS` + `CARD_IMAGE_ACCEPT` + `CARD_IMAGE_MAX_MB` +
`CARD_IMAGE_EXTENSIONS` در `src/services/flashcards/mockData.js`؛ سرور `MIME_EXTENSIONS` و
`DEFAULT_SETTINGS.media.allowedMimeTypes` را از همان می‌سازد. فرمت‌های تازه: avif، bmp، tiff، heic،
heif، ico. PDF فقط در کتابخانهٔ رسانه می‌ماند.
**تله:** `database/content/settings.json` روی پیش‌فرض‌ها را می‌پوشاند ⇒ هر دو به‌روز شد؛ و هر MIME باید
هم در `allowedMimeTypes` باشد هم در `MIME_EXTENSIONS`، وگرنه «پسوند فایل ناشناخته».

**پنل:** `MediaPicker` دو prop اختیاری گرفت — `accept` (که حالا برای پیام «فرمت پشتیبانی نمی‌شود» هم
استفاده می‌شود) و `maxMb` با پیش‌فرض `0` = خاموش؛ فقط کارت تصویری
`accept={CARD_IMAGE_ACCEPT} maxMb={CARD_IMAGE_MAX_MB}` می‌فرستد. فیلد فایل بعد از هر انتخاب پاک
می‌شود، وگرنه انتخاب دوبارهٔ همان فایلِ ردشده رویداد `change` نمی‌داد («هیچ اتفاقی نمی‌افتد»).

**داشبورد:** سقف تصویر از صدا جدا شد (`MAX_IMAGE_BYTES` ۴ مگ؛ صدا همان ۲ مگ)، `imageFileError` خالص
شد، و اگر `file.type` خالی باشد فایل با MIME درست **بازسازی** می‌شود (`typedImageFile` +
`MIME_BY_EXTENSION`) — وگرنه Data-URL بدون نوع تصویری ذخیره می‌شد و در `<img>` نمی‌آمد.

**قرارداد تازه:** `writeStore` نتیجهٔ نوشتن را در `lastWriteOk` می‌گذارد؛ `createCard`/`updateCard` در
پر شدن حافظه `Error('storage-full')` می‌دهند **و تغییر را برمی‌گردانند** تا کش با دیسک یکی بماند؛
`CardEditor` پیام فارسی می‌دهد. بقیهٔ مسیرها رفتار قبلی (ادامهٔ نشست در حافظه) را نگه داشتند.

**تأیید (بدون مرورگر، بدون build):** هارنس سرور **۴۰/۴۰** — هر ۱۲ MIME مجاز + pdf، رد zip، رد >۴ مگ —

**تلهٔ هارنس:** File پنج‌مگابایتی + نگه‌داشتن بدنهٔ base64 در آرایهٔ `calls` ⇒ SIGTERM/۱۳۷. بدنهٔ درخواست

## اصلاح بعدی کاربر (همان روز)
- hero لایه تحلیل **برگشت** (کاربر سرتیتر را می‌خواست) — حذف hero اشتباه بود؛ «سرتیتر عین بانک تست» فقط یعنی خودِ نوار بازگشت.
