# استراتژی SEO — تصمیم مستند

تاریخ: ۲۰۲۶-۱۰-۰۱ · وضعیت: **تصمیم گرفته‌شده، پیاده‌سازی معوق**

> فاز ۲۳.۷ یک «تصمیم مستند» می‌خواست، نه یک پیاده‌سازی. این سند تصمیم، دلیل،
> ریسک و مسیر rollback را ثبت می‌کند. **هیچ فایلی در `index.html` یا روتر تغییر نکرده است.**

## وضعیت فعلی (اندازه‌گیری‌شده)

| مورد | وضعیت | شاهد |
|---|---|---|
| نوع مسیریابی | **hash-based** (`#/…`) | `src/router/routeHashes.js` (۵۱ خط · ارجاع `#` = ۱۱ · `pushState` = ۰) |
| SSR / prerender | ندارد | SPA خالص با `index.html` تک‌صفحه |
| `<title>` | ۱ (ایستا، برای همهٔ viewها یکسان) | `index.html` |
| `meta description` | ۱ | `index.html` |
| Open Graph | ۵ تگ (`og:type` `og:site_name` `og:title` `og:description` `og:locale`) | `index.html` |
| Twitter card | **۰** | `index.html` |
| `rel="canonical"` | **۰** | `index.html` |
| JSON-LD | **۰** | `index.html` |
| `sitemap.xml` | **۰** | `public/` |
| `robots.txt` | **۰** | `public/` |
| `lang`/`dir` | `lang="fa"` · `dir="rtl"` | `index.html` |

**نتیجهٔ عملی:** هر view (دوره، مقاله، صفحهٔ عمومی) همان عنوان و همان توضیح را دارد و برای
خزندهٔ موتور جست‌وجو **یک URL واحد** است. محتوای عمومی — که ارزش اصلی SEO این پروژه است —
عملاً indexable نیست.

## گزینه‌ها

| گزینه | تغییر لازم | مزیت | هزینه/ریسک |
|---|---|---|---|
| **A. حفظ hash + پذیرش محدودیت** | صفر کد؛ فقط `robots.txt`/`sitemap.xml` تک-URL + twitter card | ریسک صفر · بدون تغییر معماری | صفحات عمومی هرگز جدا ایندکس نمی‌شوند |
| **B. non-hash routing + fallback سرور** | `routeHashes.js` → History API؛ سرور باید هر مسیر را به `index.html` برگرداند | URL قابل اشتراک و ایندکس‌شدنی | مسیریابی **حساس** است (`appRoute.js`/`routeHashes.js` در فهرست محافظت‌شدهٔ ممیزی) · ۱۲۸ سنجهٔ `router:test` باید بازبینی شود · لینک‌های قدیمی `#…` می‌شکنند مگر ریدایرکت اضافه شود |
| **C. prerender صفحات عمومی** | مرحلهٔ build برای فهرست محدود مسیرها (دوره، مقاله، درباره) | ایندکس‌شدن بدون تغییر روتر | artifact پیچیده‌تر · نیاز به build و تست · فهرست مسیرها باید نگه‌داری شود |
| **D. SSR/SSG کامل** | بازنویسی معماری کلاینت | بهترین SEO | نامتناسب با اندازهٔ پروژه · ریسک بالا · خارج از «حداقل تغییر» |

## تصمیم پیشنهادی

**گام ۱ (فوری، ریسک صفر): گزینهٔ A به‌عنوان وضعیت پایه** — فقط دارایی‌های ایستای بی‌خطر:
`public/robots.txt` + `public/sitemap.xml` تک-URL + twitter card در `index.html`.

**گام ۲ (نیازمند تأیید): گزینهٔ C برای صفحات عمومی** — نه گزینهٔ B.
دلیل ترجیح C بر B: B به مسیریابی **حساس و محافظت‌شده** دست می‌زند و ۱۲۸ سنجهٔ `routeHashes`/`appRoute`
را در معرض بازبینی می‌گذارد، در حالی که ارزش اصلی SEO این پروژه در **محتوای عمومی** است
(دوره، مقاله، صفحه) و همان با prerender به‌دست می‌آید بدون لمس روتر.

**گزینهٔ D رد می‌شود** در این مرحله: هزینهٔ معماری‌اش با «حداقل تغییر» و با وضعیت فعلی
پروژه (بدون staging و بدون CI پیش از این نشست) نمی‌خواند.

## چرا گام ۱ همین حالا اجرا نشد

دو پیش‌نیاز بیرونی وجود دارد که بدون آن‌ها افزودن `canonical`/`sitemap` **مضر** است نه مفید:

1. **دامنهٔ عمومی قطعی.** `sitemap.xml` و `rel="canonical"` به URL مطلق نیاز دارند.
   دامنه از `PUBLIC_SITE_URL` خوانده می‌شود (که `deploy.mjs` بدون آن در production
   متوقف می‌شود)، ولی در `index.html` **ایستا** قابل خواندن نیست. حدس‌زدن دامنه ⇒
   canonical نادرست ⇒ بدتر از نداشتن آن.
2. **build تازه.** افزودن متا به `index.html` بدون اجرای `vite build`، `dist/` را
   **کهنه** می‌کند و ادعای «artifact تازه» را باطل می‌سازد. اجرای build در این نشست
   بر اساس قاعدهٔ پروژه (بدون درخواست صریح) انجام نشد.

## مسیر اجرای گام ۱ (پس از رفع دو پیش‌نیاز)

1. تعیین `PUBLIC_SITE_URL` واقعی (تصمیم مالک پروژه).
2. `public/robots.txt` — `User-agent: *` + `Allow: /` + `Disallow: /api/` + خط `Sitemap:` با دامنهٔ قطعی.
3. `public/sitemap.xml` — تک `<url>` برای ریشهٔ دامنه (مسیرهای hash در sitemap معنا ندارند).
4. `index.html` — افزودن `twitter:card` · `twitter:title` · `twitter:description` · `rel="canonical"`.
5. `vite build` + تأیید وجود فایل‌های تازه در `dist/` (Vite پوشهٔ `public/` را کپی می‌کند).
6. اجرای `verify:all` برای اطمینان از نسنجیده‌نماندن رگرسیون.

## Rollback

| گام | rollback |
|---|---|
| فایل‌های `public/` | حذف فایل (بدون اثر زمان‌اجرا) |
| متا در `index.html` | بازگردانی از Git |
| prerender (گام ۲) | حذف مرحلهٔ build + بازگشت به SPA خالص |

## معیار پذیرش

- `robots.txt` و `sitemap.xml` در `dist/` پس از build موجود باشند.
- `sitemap.xml` با دامنهٔ **قطعی** ساخته شده باشد (نه placeholder).
- هیچ `canonical` متناقض یا دامنهٔ اشتباه در artifact نباشد.
- خروجی `verify:all` پس از تغییر سبز بماند.
