# بانک تست علوم پایه — معماری لایه

این پوشه لایهٔ «بانک تست علوم پایه تپش» است: سیستم بانک سؤال + موتور آزمون که
آزمون‌های سال‌به‌سال، تست مبحثی، آزمون شخصی‌ساز، و در آینده آزمون‌های هماهنگ /
آزمونک‌ها / پیشنهاد هوشمند / لیگ روی همین زیرساخت سوار می‌شوند.

## ساختار

```
bank/
├── TestBankLayer.jsx   ← روتر داخلی لایه (خانه، درس، سال، مبحث، کاوشگر، سازنده، تاریخچه، حل، کارنامه) + نگه‌دارندهٔ «دامنهٔ بانک»
├── BankHome.jsx        ← داشبورد ورود: سوییچر «انتخاب بانک» + کارت‌های مسیر («چطور می‌خواهی تست بزنی؟») + SubjectPicker
├── BankYears.jsx       ← آزمون‌های سال‌به‌سال (Timeline کارت‌های سال با آمار واقعی — فقط سؤال‌های رسمی)
├── BankTopics.jsx      ← تست مبحثی: درس → مبحث → زیرمبحث → تعداد
├── BankExplorer.jsx    ← کاوشگر: Filter Builder + چیپ‌های فعال + نتایج صفحه‌بندی‌شده + «آزمون من»
├── BankBuilder.jsx     ← سازندهٔ آزمون شخصی (پیش‌نمایش زندهٔ تعداد) + حالت random
├── BankSession.jsx     ← محیط حل: Practice (بازخورد فوری) / Exam (تایمر، مخفی، علامت) / Review (مرور)
├── BankResult.jsx      ← کارنامه: حلقهٔ درصد، تفکیک درس/مبحث، قوی/ضعیف، «بعدش چه بزنم؟»
├── BankHistory.jsx     ← تاریخچهٔ سشن‌ها + نشان‌شده‌ها + نیاز به مرور
├── bankShared.jsx      ← قطعات مشترک لایه (Icon، نشان‌ها، OptionButton، QuestionFigure، Modal، …)
└── bank.css            ← استایل‌های خالص با پیشوند tb- (گارد reduced-motion دارد)

├── testBankService.js  ← قرارداد API آینده + پیاده‌سازی Mock (localStorage: tapesh:testbank:v1:<userId>)
└── mockData.js         ← محتوا: درس‌ها، درخت مبحث، ۴۷ سؤال با تحلیل و آمار جامعه + دو محور طبقه‌بندی
```

## دو محور طبقه‌بندی محتوا

هر سؤال دو برچسب دارد و هر دو از **خود رکورد سؤال** مشتق می‌شوند (هیچ فهرست دستی
جدا نگه‌داری نمی‌شود)؛ پس افزودن محتوای جدید یا اتصال Backend نیازی به تغییر UI ندارد:

| محور | مقدارها | مشتق از | معنی |
|---|---|---|---|
| `bankKind` (نوع بانک) | `national` / `authored` | `SOURCE_BANK[question.source]` | «بانک تست کشوری» (official + comprehensive) در برابر «بانک تست تألیفی» (tapesh) |
| `track` (رشته) | `medicine` / `dentistry` | `question.track` | «علوم پایه پزشکی» در برابر «علوم پایه دندان‌پزشکی» |

- **در داده:** `BANK_KINDS`، `TRACKS`، `SOURCE_BANK` در `mockData.js` + تابع‌های مشتق
  `bankKindOf` / `trackOf` / `questionsByBank` / `questionsByTrack` و `buildStats(questions)`.
- **در سرویس:** `bankKinds` و `tracks` فیلد استاندارد `EMPTY_FILTERS` و blueprint سشن‌اند؛
  `scopeToFilters` / `normalizeScope` / `scopeLabel` شکل واحد «دامنه» را می‌سازند.
- **در UI:** `BankScopeSwitcher` در `BankHome` (دو محور مستقل، هر کدام با گزینهٔ «همه») +
  گروه‌های «نوع بانک» و «رشته» در پنل فیلتر کاوشگر + نشان‌های `BankKindBadge` / `TrackBadge`
  روی کارت‌های نتیجه و سربرگ سؤال.

### جریان «دامنه»

`TestBankLayer` یک state به نام `scope` دارد و تنها جای نگه‌داری انتخاب کاربر است.
همهٔ فیلترهایی که به سرویس می‌روند از `withScope(filters)` عبور می‌کنند، پس تمرین، آزمون،
تست مبحثی، آزمون سال‌به‌سال و کاوشگر خودکار داخل دامنه می‌مانند. `fetchBankOverview(userId, scope)`
هم آمار بانک/درس‌ها/مبحث‌ها/برچسب‌ها را درون دامنه می‌سازد و در عوض نقشهٔ شمارندهٔ کل بانک
را در `banks` و `tracks` برمی‌گرداند تا سوییچر همیشه عدد واقعی داشته باشد.
نکته: «آزمون سال‌به‌سال» فقط از سؤال‌های `source === 'official'` ساخته می‌شود؛ پس شمارش
هر سال دقیقاً همان چیزی است که آزمون اجرا می‌کند (و در دامنهٔ «تألیفی» این نما خالی است
و راهنمای تغییر دامنه نشان می‌دهد).

## اصول کلیدی

1. **جدایی داده از UI** — UI هیچ‌وقت به mockData وارد نمی‌شود؛ همه‌چیز از سرویس.
2. **حلّهٔ سؤال سمت سرویس** — blueprint فیلتر/تعداد به `createSession` می‌رود و سشن
   با `questionIds` ساخته می‌شود. موتور پیشنهاد آینده فقط همین blueprint را عوض می‌کند.
3. **کلید پاسخ در کلاینت نیست (PHASE 2)** — بانک عمومی (`/api/public/test-bank/questions`)
   و Bundle هیچ `correctAnswer`/`explanation`/`optionPercents` ندارند. درستی، نمره و
   پاداش را سرور تعیین می‌کند (`POST /api/users/test-bank/answers` و
   `/test-bank/grade`) و کلید **فقط پس از ثبت پاسخ** و فقط برای همان سؤال برمی‌گردد
   (بازگشایی کنترل‌شده). `fetchReviewSession` هم کلید را از همان مسیر می‌گیرد.
   تست نگهبان: `npm run bank:test`.
4. **وضعیت کاربر مشتق است** — «حل‌شده/غلط/دقت پایین» از خود سشن‌ها محاسبه می‌شود،
   نه فیلد دستی؛ نشان‌شده و نیاز به مرور در state کاربر ذخیره می‌شوند.
5. **زمان سشن از سرویس** — `endsAt` در `createSession` صادر می‌شود؛ Timer فقط نمایش می‌دهد.
6. **سازگاری Design System** — فونت Doran/Pinar، سبز `#61D192`، بنفش انتخاب `#937fcd`،
   اعداد فارسی از leagueShared، کاهش حرکت مطابق سیاست کل داشبورد.

## ورود به لایه

از `TestsSection` (کارت بزرگ «بانک تست علوم پایه» و کارت «آزمون های شخصی») →
`DashboardLayout` لایه را با نوشتن در **مسیر داشبورد** mount می‌کند؛ state بولی
جداگانه‌ای وجود ندارد. بستن/تغییر سکشن، لایه را unmount می‌کند (الگوی سایر لایه‌ها).

### نمای داخلی لایه روی آدرس می‌نشیند

`TestBankLayer` دیگر `initialView` نمی‌گیرد؛ نما را از هوک مشترک
`useLayerRoute` می‌خواند و می‌نویسد:

```jsx
const [view, setView] = useLayerRoute(LAYER_IDS.testBank, TEST_BANK_HOME, {
  volatile: TEST_BANK_VOLATILE,   // ['live'] — اتاق آزمون در حال اجرا
  screenOf: testBankScreenOf,     // topics/subject با شناسهٔ درس تفکیک می‌شوند
});
```

`TEST_BANK_HOME` و `testBankScreenOf` در بالای همان فایل و خارج از کامپوننت
تعریف شده‌اند (هوک انتظار `initialView` ثابت دارد). `TestsSection` برای کارت
«آزمون شخصی» فقط `openLayer(LAYER_IDS.testBank, { name: 'builder', … })` صدا می‌زند.

قرارداد نوشتن (پیاده‌سازی‌شده در `src/layout/dashboard/dashboardRoute.jsx`):

- تغییر **صفحه** (home → builder → result) یک ورودی تاریخچه می‌سازد → Back/Forward
  داخل لایه کار می‌کند.
- تغییر **درون همان صفحه** (پیش‌نمایش تعداد، فیلترها) ورودی فعلی را به‌روز می‌کند
  و تاریخچه را شلوغ نمی‌کند.
- نماهای `volatile` (`live` و …) هرگز در آدرس نمی‌نشینند تا رفرش به یک آزمون
  نیمه‌کاره نیفتد.
- برای نمای داده‌محور `result` که مستقیماً (رفرش/لینک) باز می‌شود، یک افکت
  `restoredRef` کارنامه را از سرویس با `sessionId` موجود در view بازمی‌خواند.

مستند کامل مسیر/آدرس و باگ‌های Back-Forward و رفرش: بخش «ناوبری داشبورد» در
`src/layout/dashboard/dashboardRoute.jsx`.
